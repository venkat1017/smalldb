1. Project setup: start from an empty folder

Before we talk about database internals, we need a project that you can actually run. This part may look basic, but it matters for the teaching style of the rest of the chapter. We are not going to pretend that main.go, go.mod, imports, and a working command already exist. We will create them from nothing.

Step 0A — make sure Go is available

Open a terminal and ask Go for its version:

You should see a line beginning with go version. The exact version and operating system can differ. If the shell says that go is not found, install Go first and come back when this command works. Everything else in the chapter assumes the Go toolchain is available.

How we will edit the project from here

We will mostly stay in this one main.go file for Part 1 so storage ideas are not hidden behind package structure. That is a teaching choice, not a claim that every production Go project should have one file.

Each section will tell you one of three things: add a declaration, change an existing declaration, or temporarily replace the body of main so we can test the newest concept. This temporary main is our laboratory. Near the end we replace it with the command shell.

Important workshop ruleDo not wait until the end to run the code. Type a small change, run gofmt -w main.go, then run go run . whenever a checkpoint appears. 2. What are we actually building?

When people first learn databases, they often meet them from the outside: SQL statements go in, rows come out. That interface is useful, but it hides the part we want to understand. In this chapter we will work one layer lower. We will ask: if we were forbidden from using SQLite, PostgreSQL, BoltDB, Badger, or any storage library, what is the smallest thing we could build that still deserves to be called persistent storage?

Our answer will be intentionally primitive. There is one file named minidb.db. There is one kind of row, a user. A user has an ID, name, email, and age. We support four operations: INSERT, GET, SCAN, and DELETE. There is no SQL parser, no B-tree, no transactions, no query optimizer, and no concurrency control.

That sounds almost too small. Good. The smaller the system, the easier it is to see the ideas that production databases later make more sophisticated.

The question that drives the whole chapterIf our Go process exits, how can another process started tomorrow recover the same users?

If you can answer that question precisely—not with “the database saves it,” but with which bytes are written where and how they are interpreted later—you have crossed an important line in systems programming.

3. RAM, disk, and the persistence problem

Start with ordinary Go data:

users := []string{"alice", "bob", "charlie"}
fmt.Println(users)

While the program runs, the slice metadata and the strings are represented in memory. That memory is convenient because the CPU can access it quickly, but it belongs to the running process. When the process ends, we cannot expect those bytes to remain available as our durable database state.

RAM

Fast and directly useful to the running program. Excellent for variables, caches, stacks, heaps, and temporary state.

But process memory is not our long-term source of truth.

Persistent storage

A file on durable storage can outlive the process that created it. A later process can open the file and read the bytes again.

That makes the file a candidate for database state.

So the first version of a database can be described without any database vocabulary:

First principleA database engine is a program that turns in-memory values into a stable byte representation, writes those bytes to persistent storage, and later reverses the process.

The verbs matter. We need to encode values into bytes, choose where those bytes live, write them, later read them, and finally decode them back into useful values. Almost everything else in a database grows from making those five actions faster, safer, more concurrent, and more flexible.

4. A file is only bytes

A common beginner mistake is to imagine a file as if it already understands rows. It does not. The operating system gives us a byte sequence. We may ask to read bytes starting at position 500, or write bytes starting at position 128, but the file itself does not know that positions 128 through 383 are “Alice.” That meaning exists only because our program establishes a convention.

Imagine the file as a very long numbered tape:

byte 0, byte 1, byte 2, byte 3, ...

If we write the UTF-8 bytes for alice, the file receives five byte values. If we write the integer 30, we must decide how many bytes represent it and in which byte order. If we write two records back to back, we must know where the second begins. Nothing in the file answers those questions for us.

This is what a file format is: an agreement between the writer and the reader about the meaning of byte positions.

Teacher's testIf I hand you a hex dump of the file, you should eventually be able to point to a group of bytes and say, “these four bytes are the age,” or “these eight bytes identify the format version.” If you cannot do that, the format is still too vague in your head.

5. Inventing our first on-disk format

We need a layout for a user record. The easiest design is fixed-size records: every record occupies exactly the same number of bytes. That is wasteful, but the arithmetic becomes beautifully simple.

Let us reserve 256 bytes for every user:

ID
8
deleted
1
name
32
email
64
age
4
unused/padding
147
8 + 1 + 32 + 64 + 4 + 147 = 256 bytes

Why 256? Not because 256 is magical. It is simply a convenient fixed size for the exercise. We could choose 128, 300, or 512. What matters is that both the writer and reader agree.

The first nine bytes are easy: eight bytes for a signed-looking ID that we encode as a 64-bit value, then one byte that acts as a deletion marker. After that, the name gets exactly 32 bytes and the email gets exactly 64 bytes. The age gets four bytes. The rest is unused.

Immediately, two problems should bother you. A two-character name wastes most of its 32-byte region. A long email may not fit. Do not solve those yet. Those problems are valuable because they will motivate variable-length records and pages later. Good systems courses often become confusing when they introduce sophisticated machinery before the student has personally felt the simpler design fail.

Deliberate limitationFor this version we will reject names longer than 32 bytes and emails longer than 64 bytes. Silent truncation is easy to demonstrate but dangerous as an API: the caller might believe one value was stored while a different value was actually persisted.

Fixed-size versus variable-size

We choose fixed-size records because our learning goal is not “build an efficient database in one chapter.” Our goal is to make direct file access obvious.

6. The most important equation in Part 1

Suppose the first 128 bytes of the file are reserved for a header. Records begin immediately after that header, and every record is 256 bytes. We will give our first user ID 1.

Where should ID 1 live? Immediately after the header, at byte 128. Where should ID 2 live? One record later, at byte 384. ID 3 begins at byte 640.

That pattern gives us:

recordOffset(id) = HeaderSize + (id - 1) × RecordSize
IDCalculationOffset
1128 + (1 − 1) × 256128
2128 + (2 − 1) × 256384
3128 + (3 − 1) × 256640

This one equation is the reason fixed-size records are so easy to retrieve. To fetch ID 900, we do not need to read IDs 1 through 899. We calculate one byte position and ask the operating system to read 256 bytes from there.

Complexity intuitionFinding the byte position is O(1): the arithmetic takes constant work regardless of how many records exist. That does not mean the whole database is magically fast—disk I/O still matters—but it explains the attraction of direct addressing.

TYPE 1Add the file-format constants

You already have package main, the fmt import, and the temporary main() from setup. Do not replace the whole file. Add this constant block between the import and main():

const (
    HeaderSize  = 128
    RecordSize  = 256
    MaxNameLen  = 32
    MaxEmailLen = 64
)

These constants are not mere implementation details. Once a real database file exists, changing them can make old files unreadable. On-disk formats are APIs to your future software.

TYPE 2Encode the offset rule once

Add this function below the constants:

func recordOffset(id int64) int64 {
    return int64(HeaderSize) + (id-1)*int64(RecordSize)
}

Putting the equation in a helper is more important than it looks. If Insert, Get, and Delete each repeat the arithmetic independently, one small mismatch can corrupt your mental model and your file. One function means one rule.

Now temporarily replace only the body of main() with:

func main() {
    fmt.Println("id=1 offset=", recordOffset(1))
    fmt.Println("id=2 offset=", recordOffset(2))
    fmt.Println("id=3 offset=", recordOffset(3))
}

7. Why put a header at the front?

Why waste the first 128 bytes? Because a raw file needs identity. Imagine opening a random file and treating bytes 128–383 as one of our records. Without metadata, we have no quick way to know whether the file is actually ours or whether it was written by an incompatible version of the program.

We will put two pieces of metadata in the header:

Header bytesMeaning
0–7Eight “magic” bytes: MINIDB01
8–11A 32-bit format version, starting at 1
12–127Reserved for future metadata

A magic value is simply a recognizable signature. Many file formats use one. It lets the reader reject nonsense early instead of interpreting arbitrary bytes as valid database state.

The version serves a different purpose. Suppose Part 6 of our project changes the record layout. Version metadata gives newer code a chance to say, “I understand version 1” or “this is version 3 and I need a migration path.”

TYPE 3Define the in-memory store

We are about to mention os.File, so expand the import section first:

import (
    "fmt"
    "os"
)

Then add the store type below recordOffset:

type Store struct {
    file *os.File

Notice what Store does not contain: it does not contain a slice of all users. The file is the durable state. Store is primarily a handle through which our code performs reads and writes.

TYPE 4Teach the program to write a new header

First, think in English:

  1. Open the path for reading and writing. Create it if it does not exist.
  2. Ask for its current size.
  3. If the size is zero, this is a new file, so write our header.
  4. If it already contains data, validate the header before trusting it.

This step needs encoding/binary. Add it to the import block so the imports are now "encoding/binary", "fmt", and "os".

Now type only the initialization idea:

func writeNewHeader(file *os.File) error {
    header := make([]byte, HeaderSize)
    copy(header[0:8], []byte("MINIDB01"))
    binary.LittleEndian.PutUint32(header[8:12], 1)

    _, err := file.WriteAt(header, 0)
    return err
}

This is our first encounter with endianness. An integer is larger than one byte, so we need a rule for which byte stores which part of the number. We choose little-endian and use the same rule when reading. You do not need to memorize byte-order history. The important lesson is consistency: bytes have no inherent “uint32” type, so the format must specify how an integer becomes bytes.

Why WriteAt?It makes the location explicit. “Write these bytes at offset 0” mirrors the way we are reasoning about the file. Later, records will be written at their calculated offsets.

TYPE 5Now build Open in two small pieces

Writing a header is only half of opening a database. Existing files need to be checked before we trust them. First add a validator:

func validateHeader(file *os.File, size int64) error {
    if size < int64(HeaderSize) {
        return fmt.Errorf("database file is too small to contain a valid header")
    }

    header := make([]byte, HeaderSize)
    if _, err := file.ReadAt(header, 0); err != nil {
        return err
    }

    if string(header[0:8]) != "MINIDB01" {
        return fmt.Errorf("not a MiniDB file: bad magic bytes")
    }

    version := binary.LittleEndian.Uint32(header[8:12])
    if version != 1 {
        return fmt.Errorf("unsupported database version %d", version)
    }

    dataBytes := size - int64(HeaderSize)
    if dataBytes%int64(RecordSize) != 0 {
        return fmt.Errorf("database file has a partial/corrupt record region")
    }

    return nil
}

Read that slowly. We are not checking user data yet. We are checking whether the container itself has the shape our program expects: enough bytes for a header, the right magic value, a version we understand, and a record area whose size is divisible by 256.

Now add the real Open function and a matching Close:

func Open(path string) (*Store, error) {
    file, err := os.OpenFile(path, os.O_RDWR|os.O_CREATE, 0644)
    if err != nil {
        return nil, err
    }

    info, err := file.Stat()
    if err != nil {
        file.Close()
        return nil, err
    }

    if info.Size() == 0 {
        if err := writeNewHeader(file); err != nil {
            file.Close()
            return nil, err
        }
    } else if err := validateHeader(file, info.Size()); err != nil {
        file.Close()
        return nil, err
    }

    return &Store{file: file}, nil
}

func (s *Store) Close() error {
    return s.file.Close()
}

Temporarily replace main() again so it does one job: open a database and close it.

func main() {
    store, err := Open("lesson.db")
    if err != nil {
        fmt.Println("open error:", err)
        return
    }
    defer store.Close()

    fmt.Println("opened lesson.db successfully")
}

8. Separate the storage problem from the encoding problem

Before writing Insert, resist the urge to mix everything into one function. There are actually two different jobs:

Job A: turn a Go value into exactly 256 bytes. Job B: decide where those 256 bytes belong in the file and write them there.

If we separate those jobs, Insert becomes easy to read and Get can reuse the reverse transformation.

Our in-memory value

Add this type next to Store. It is safe for the type to exist before we have any users in the file.

type User struct {
    ID      int64
    Deleted bool
    Name    string
    Email   string
    Age     int32
}

This struct is an in-memory representation. Do not assume Go's struct layout is automatically our disk format. Compilers may insert padding, representation details can matter, and directly dumping memory would couple the file format to implementation details. We will explicitly encode each field.

TYPE 6Encode one user

No new import is needed here: fmt and encoding/binary are already present. Add:

func encodeUser(u User) ([]byte, error) {
    if len([]byte(u.Name)) > MaxNameLen {
        return nil, fmt.Errorf("name is longer than %d bytes", MaxNameLen)
    }
    if len([]byte(u.Email)) > MaxEmailLen {
        return nil, fmt.Errorf("email is longer than %d bytes", MaxEmailLen)
    }

    record := make([]byte, RecordSize)
    binary.LittleEndian.PutUint64(record[0:8], uint64(u.ID))

    if u.Deleted {
        record[8] = 1
    }

    copy(record[9:41], []byte(u.Name))
    copy(record[41:105], []byte(u.Email))
    binary.LittleEndian.PutUint32(record[105:109], uint32(u.Age))

    return record, nil
}

Read the indexes as a map. Bytes 0 through 7 hold the ID. Byte 8 is the tombstone. The name begins at 9 and stops just before 41, giving 32 bytes. Email occupies 41 through 104, giving 64 bytes. Age occupies 105 through 108, giving 4 bytes. Everything from 109 through 255 remains zero.

The zero-filled remainder is not doing anything useful yet. It exists because our record contract says “256 bytes every time.” That waste is not a bug in our implementation; it is a consequence of our design choice.

TYPE 7Decode the same bytes

Decoding text needs one new standard-library package. Add "strings" to the import block, then add:

func decodeUser(record []byte) (User, error) {
    if len(record) != RecordSize {
        return User{}, fmt.Errorf("expected %d bytes, got %d", RecordSize, len(record))
    }

    u := User{
        ID:      int64(binary.LittleEndian.Uint64(record[0:8])),
        Deleted: record[8] == 1,
        Name:    strings.TrimRight(string(record[9:41]), "\x00"),
        Email:   strings.TrimRight(string(record[41:105]), "\x00"),
        Age:     int32(binary.LittleEndian.Uint32(record[105:109])),
    }

    return u, nil
}

Why trim \x00? If the name is Al, only two bytes in its 32-byte region are used. The remaining bytes are zero because make([]byte, RecordSize) creates a zero-filled slice. When we decode, we remove those trailing zero bytes so the in-memory string becomes Al, not Al followed by thirty NUL characters.

Checkpoint: pretend to be the decoder

If bytes 9–13 contain alice and bytes 14–40 are zero, what string should the decoder return? If byte 8 changes from 0 to 1 while every other byte stays the same, what changed logically? If you can answer those immediately, the record layout is becoming real.

Now test the encoder and decoder without touching the file. Replace the temporary main() body with:

func main() {
    original := User{ID: 1, Name: "alice", Email: "alice@example.com", Age: 30}

    record, err := encodeUser(original)
    if err != nil {
        fmt.Println("encode error:", err)
        return
    }

    decoded, err := decodeUser(record)
    if err != nil {
        fmt.Println("decode error:", err)
        return
    }

    fmt.Printf("%+v\n", decoded)
}

9. Build INSERT from pieces we already understand

Only now are we ready to insert. Notice how little new theory is required. We already know how to encode a record and where a record with a given ID belongs.

We still need one decision: how do we choose the next ID? Our simple file is append-only with respect to record slots. If the file contains N complete record slots after the header, the next ID is N + 1.

numberOfRecords = (fileSize − HeaderSize) / RecordSize

If the file is exactly 128 bytes, it contains zero records. If it is 384 bytes, it contains one 256-byte record after the header. If it is 640 bytes, it contains two.

TYPE 8Find the next ID

func (s *Store) nextID() (int64, error) {
    info, err := s.file.Stat()
    if err != nil {
        return 0, err
    }

    count := (info.Size() - int64(HeaderSize)) / int64(RecordSize)
    return count + 1, nil
}

This works because we never physically remove a record slot. Deleting a user only flips a flag. Therefore the file size still tells us how many slots have ever been allocated.

TYPE 9Insert one record

func (s *Store) Insert(name, email string, age int32) (int64, error) {
    id, err := s.nextID()
    if err != nil {
        return 0, err
    }

    record, err := encodeUser(User{
        ID:    id,
        Name:  name,
        Email: email,
        Age:   age,
    })
    if err != nil {
        return 0, err
    }

    if _, err := s.file.WriteAt(record, recordOffset(id)); err != nil {
        return 0, err
    }

    return id, nil
}

Read this function almost like a sentence: get an ID; encode a user; calculate its slot; write the bytes. The function is short because we pushed detailed concerns into helpers whose names carry meaning.

A systems-design habit worth keepingWhen a low-level function feels impossible to understand, look for multiple concepts that have been collapsed together. Separating “encode,” “locate,” and “write” often turns one dense block into three obvious ideas.

Time to combine the pieces for the first time. Replace main() with this small experiment:

func main() {
    store, err := Open("lesson.db")
    if err != nil {
        fmt.Println("open error:", err)
        return
    }
    defer store.Close()

    id, err := store.Insert("alice", "alice@example.com", 30)
    if err != nil {
        fmt.Println("insert error:", err)
        return
    }

    fmt.Println("inserted id=", id)
}
Run checkpoint 4If lesson.db is still the 128-byte file from checkpoint 2, run go run . once. Alice should receive ID 1. Check the file size afterward: it should now be 384 bytes = 128-byte header + one 256-byte record. If you run the program again without deleting the file, it inserts another record and the ID increases. That behavior is coming from file size, not from an in-memory counter.

What persistence have we achieved?

After a successful write, the operating system has accepted our bytes for the file. On a normal close and restart, we expect to read them again. That is enough for this chapter's persistence experiment.

It is not yet transaction durability. A power loss at the wrong time, torn writes, storage errors, or a crash between multiple related writes can still leave state we do not know how to repair. Later database mechanisms such as journaling and write-ahead logging exist because “I called Write” is not the end of the reliability story.

10. GET is the inverse of INSERT

To retrieve a user by ID, we should not scan from the beginning. Fixed-size records bought us a direct address. The procedure is:

  1. Validate that the ID is positive.
  2. Calculate recordOffset(id).
  3. Read exactly 256 bytes from that position.
  4. Decode those bytes.
  5. If the tombstone is set, report the row as deleted.

Get needs two more standard packages: "errors" for comparing domain errors and "io" for recognizing an attempted read beyond the end of the file. Add both to the import block.

Before writing the function, define two domain errors so callers can distinguish “missing” from “deleted” without matching strings:

var (
    ErrNotFound = errors.New("record not found")
    ErrDeleted  = errors.New("record deleted")
)

TYPE 10Read one record slot

func (s *Store) Get(id int64) (User, error) {
    if id < 1 {
        return User{}, ErrNotFound
    }

    record := make([]byte, RecordSize)
    if _, err := s.file.ReadAt(record, recordOffset(id)); err != nil {
        if errors.Is(err, io.EOF) {
            return User{}, ErrNotFound
        }
        return User{}, err
    }

    u, err := decodeUser(record)
    if err != nil {
        return User{}, err
    }
    if u.Deleted {
        return User{}, ErrDeleted
    }
    return u, nil
}

The important line is still the offset calculation. We jump directly to the record's slot. The decoder then gives meaning back to those bytes.

There is a subtle philosophical point here: the ID is both logical data and part of our addressing scheme. Because IDs are dense and monotonically increasing, we can map them to slots with arithmetic. Real databases usually cannot rely on such a simple relationship, which is why indexes become essential.

Test the read path immediately. You do not need to insert again if lesson.db already contains Alice:

func main() {
    store, err := Open("lesson.db")
    if err != nil {
        fmt.Println("open error:", err)
        return
    }
    defer store.Close()

    user, err := store.Get(1)
    if err != nil {
        fmt.Println("get error:", err)
        return
    }

    fmt.Printf("id=%d name=%s email=%s age=%d\n",
        user.ID, user.Name, user.Email, user.Age)
}

11. SCAN shows us the cost we have been avoiding

GET 900 is cheap because ID 900 tells us where to jump. But what if we want “all users”? Or “the user whose email is bob@example.com”? Without an index on email, the only general strategy is to inspect records one by one.

That is a scan.

TYPE 11Count slots, then visit each ID

func (s *Store) Scan() ([]User, error) {
    info, err := s.file.Stat()
    if err != nil {
        return nil, err
    }

    count := (info.Size() - int64(HeaderSize)) / int64(RecordSize)
    users := make([]User, 0, count)

    for id := int64(1); id <= count; id++ {
        u, err := s.Get(id)
        if errors.Is(err, ErrDeleted) {
            continue
        }
        if err != nil {
            return nil, err
        }
        users = append(users, u)
    }

    return users, nil
}

This is deliberately straightforward, even a little inefficient. We repeatedly call Get so the deletion logic and decoding stay in one place. Later, once performance matters, we might scan sequential bytes more efficiently. But clarity wins today.

Now feel the future problemIf there are 10 records, scanning is fine. If there are 10 million records and we need one email address, reading every record is a terrible plan. What data structure could tell us where to jump? That question will eventually lead us toward indexes and B-trees.

For a small practical check, temporarily make main() call store.Scan() and loop over the returned users. Do not build the command shell yet. The important thing is to see that Scan is only orchestration over the Get primitive you already trust.

Run checkpoint 6Insert two or three users with the previous temporary main(), then switch main() to a scan test. Confirm that every allocated, non-deleted record appears. This is a good moment to inspect how the time would grow if the file had thousands of slots instead of three.

12. DELETE without moving anything

Physical deletion is awkward in a fixed-slot file. Suppose record 2 sits between records 1 and 3. If we removed its 256 bytes from the middle of the file, record 3 would move. Then our beautiful mapping between ID and offset would break.

So we take the lazy option: keep the slot, but mark it dead. That marker is usually called a tombstone.

Because our tombstone is exactly byte 8 inside the record, deletion can be extremely small: verify the record exists, then write one byte.

TYPE 12Flip the tombstone

func (s *Store) Delete(id int64) error {
    if _, err := s.Get(id); err != nil {
        return err
    }

    _, err := s.file.WriteAt([]byte{1}, recordOffset(id)+8)
    return err
}

This teaches two useful ideas at once. First, deletion can be a logical state change rather than physical removal. Second, random-access writes do not need to rewrite an entire file—or even an entire record—when the format gives us a precise location.

Of course, the tombstone leaves a hole. If half the records are deleted, half the record area is wasted. Later we might maintain a free list so new inserts reuse deleted slots, or compact the file. Again, a database feature appears naturally because the naive design develops a pain point.

Test deletion in two stages: call Delete(1), then call Get(1). The second call should return ErrDeleted. Also check the file size: deleting the record must not shrink the file, because the 256-byte slot still exists.

Run checkpoint 7This is the moment to connect the logical word “delete” to the physical reality: one byte changed from 0 to 1. We will verify that directly with xxd in the inspection section.

13. Add a tiny shell only after the storage layer works

It is tempting to begin with command parsing because a prompt feels like a database. But the command shell is not the interesting part. We intentionally postponed it until the storage API had a clear shape.

Our shell will understand:

INSERT alice alice@example.com 30
GET 1
SCAN
DELETE 1
EXIT

We will use strings.Fields, so names cannot contain spaces in this toy interface. That is a parser limitation, not a storage limitation. A real SQL parser is a separate project.

The main loop is conceptually simple:

  1. Print minidb>.
  2. Read one line.
  3. Split it into fields.
  4. Dispatch on the first word.
  5. Call the storage method.
  6. Print the result or error.
Layering mattersThe shell should not calculate byte offsets. Insert should not know how terminal input is tokenized. The CLI is one layer; the store is another. Even tiny projects are easier to reason about when responsibilities stay separate.

TYPE 13Turn the temporary main() into a prompt

The interactive shell needs bufio, so add "bufio" to the imports. Start with a loop that only reads input and recognizes EXIT. This isolates terminal I/O before command parsing:

scanner := bufio.NewScanner(os.Stdin)

for {
    fmt.Print("minidb> ")
    if !scanner.Scan() {
        fmt.Println()
        break
    }

    line := strings.TrimSpace(scanner.Text())
    if strings.EqualFold(line, "EXIT") {
        return
    }

    fmt.Println("you typed:", line)
}

Put that loop inside main() after opening the database. Run it and type a few lines. At this stage the shell is intentionally stupid; we are proving the read-evaluate-loop shape first.

TYPE 14Split one command into words

Replace the line/echo portion with:

parts := strings.Fields(scanner.Text())
if len(parts) == 0 {
    continue
}

command := strings.ToUpper(parts[0])
fmt.Println("command:", command, "arguments:", parts[1:])

Now type INSERT alice alice@example.com 30. You should see that the first token is the command and the remaining tokens are arguments. This is the tiny parser our toy shell needs.

TYPE 15Dispatch to storage methods

At this point, add a switch command. Do it one case at a time: first SCAN because it needs no argument parsing, then GET and DELETE, and finally INSERT. The numeric commands need strconv, so add "strconv" when you reach them.

For example, the GET branch should do three jobs and no more: verify there are two tokens, parse the ID, then call store.Get(id). The branch should never know that an ID maps to HeaderSize + (id-1)*RecordSize. That remains the storage layer's responsibility.

Run checkpoint 8Once your four cases are wired, start the program and manually execute INSERT → GET → SCAN → DELETE → SCAN → EXIT. If something fails, test the individual storage method again before blaming the parser.

We intentionally have not pasted the finished switch here. You have already written every storage operation it calls. The complete CLI wiring appears once, at the end, where you can compare your version with the assembled program.

14. The most important practical exercise: inspect the bytes

If you only run commands and see friendly output, the project can still feel magical. The cure is to open the database file with a hex viewer.

After building the final program, try:

go build -o minidb .
./minidb minidb.db

minidb> INSERT alice alice@example.com 30
inserted id=1
minidb> INSERT bob bob@example.com 25
inserted id=2
minidb> EXIT

xxd -g 1 -l 700 minidb.db

Do not rush past the output. Find the ASCII bytes for MINIDB01 at the beginning. Then move to offset 128, where record 1 begins. The first eight bytes encode ID 1. Byte 136—eight bytes after the start of the record—is the deleted flag. Soon after that you should see the characters of alice. At offset 384, record 2 begins.

Now delete Alice and inspect again:

./minidb minidb.db
minidb> DELETE 1
record 1 deleted
minidb> EXIT

xxd -g 1 -s 128 -l 32 minidb.db

Most of the first record should be unchanged. The tombstone byte should now be 01. You have just watched a logical database operation become one byte mutation on disk.

Checkpoint: persistence test

Insert two users. Exit the process completely. Start it again with the same file. Run SCAN. If the users reappear, the second process did not “remember” them in RAM; it reconstructed them from your file format. That is the core achievement of Part 1.

Try a corruption experiment

Make a copy first. Then modify a byte inside a name or age field and run GET. Our current program has no checksum, so it may happily decode corrupted bytes as if they were legitimate. That is not a surprising failure; it is a missing feature. Detection requires extra information such as checksums, structural validation, or stronger page formats.

This is an important engineering mindset: reliability features are not decorative. Each one answers a concrete failure mode.

15. What our database gets wrong—and why that is useful

Our tiny store is enough to teach persistence, byte layouts, direct addressing, encoding, scanning, and tombstones. It is nowhere near enough for production use. The deficiencies are the syllabus for the next parts.

PainWhere it comes fromWhat it motivates
Wasted spaceEvery name gets 32 bytes and every email gets 64 even when values are tiny.Variable-length cells, slotted pages, overflow storage.
Hard field limitsFixed regions cannot hold arbitrarily long values.Length-prefixed values and overflow pages.
Slow search by non-ID fieldsThere is no structure mapping email or name to a record location.Indexes, commonly B-trees or related structures.
Deleted space is wastedTombstones preserve slots forever.Free lists, slot reuse, vacuum/compaction.
No atomic multi-step changesWrites happen directly to the main file.Journaling or write-ahead logging.
No crash recoveryWe do not record enough intent to repair interrupted updates.Recovery protocols, checksums, WAL.
No concurrency protocolTwo writers can race without coordination.Locks, latches, MVCC, transaction isolation.
No caching strategyWe delegate everything to basic file reads/writes.Pages and a buffer pool.

The “pages” idea should now feel motivated

Production databases rarely think in terms of “one application record equals one arbitrary file write.” They organize storage into pages: fixed-size blocks that become units of I/O, caching, checksumming, locking, and recovery. Once records can be variable-length, a page also needs metadata describing where its cells live.

If we introduced pages at the beginning, they would look like ceremony. After building this version, we can see what they solve. That is the learning strategy for the whole MiniSQLite series: build the naive thing, observe exactly where it hurts, then introduce one mechanism that answers that pain.

One subtle issue: clean persistence is not crash safety

There is a temptation to say, “we wrote to disk, therefore it is durable.” Real storage stacks are more complicated. The operating system may buffer writes. Devices may have their own caches. A process can crash after one write but before another. A machine can lose power during an update. Files can be partially written or corrupted.

fsync/Sync can be part of a durability story, but even that is not a transaction protocol. If one logical transaction needs to update multiple pieces of state, we need a way to recover after interruption. That is why databases develop journals or WALs. Part 1 does not solve this; it names the boundary honestly.

Another subtle issue: bytes versus characters

Our limits are byte limits, not “human character” limits. UTF-8 characters can use more than one byte. A 32-character name is not guaranteed to fit in 32 bytes. This is another reason fixed-size text fields become awkward. For the exercise, think in terms of byte storage, because that is what the file ultimately contains.

16. Suggested exercises before looking at the complete program

Try these in order. They are designed to check whether you understand the mechanics rather than whether you can copy syntax.

  1. Offset drill. Without running code, compute the starting byte of IDs 1, 2, 7, and 1000. Then verify by printing recordOffset.
  2. Persistence drill. Insert three users, exit, restart, and fetch all three. Explain in one paragraph why the second process can reconstruct them.
  3. Hex drill. Use xxd to find the header, ID, tombstone, name, email, and age of the first record.
  4. Tombstone drill. Record the first 32 bytes of a row before and after deletion. Identify the exact byte that changes.
  5. Space drill. For name A and email a@b.co, calculate how many bytes in the 256-byte record are semantically useful and how many are reserved/unused.
  6. Scale drill. Insert 10,000 records and time SCAN. Repeat with 100,000. Explain why runtime should grow roughly with the number of records.
  7. Design drill. Sketch, without coding, how you might reuse deleted slots. What extra metadata would you need?
  8. Reliability drill. List three moments where a crash could leave surprising state. Do not fix them yet; just identify the failure modes precisely.

17. Complete program — now assemble what we built

At this point your project is still intentionally small:

minisqlite/ ├── go.mod ├── main.go ├── lesson.db ← created during checkpoints; safe to delete when you want a clean test └── minidb.db ← created when you run the finished CLI

lesson.db is not source code. It is a binary artifact produced by your program. Keeping that distinction clear—program versus persisted state—is part of the lesson.

Only read this after the incremental sections

The final file should feel like a collection of ideas you already understand: header validation, one record layout, one offset equation, explicit encode/decode helpers, and four operations layered on top.

package main

import (
    "bufio"
    "encoding/binary"
    "errors"
    "fmt"
    "io"
    "os"
    "strconv"
    "strings"
)

const (
    HeaderSize  = 128
    RecordSize  = 256
    MaxNameLen  = 32
    MaxEmailLen = 64
)

var (
    ErrNotFound = errors.New("record not found")
    ErrDeleted  = errors.New("record deleted")
)

type Store struct {
    file *os.File
}

type User struct {
    ID      int64
    Deleted bool
    Name    string
    Email   string
    Age     int32
}

func recordOffset(id int64) int64 {
    return int64(HeaderSize) + (id-1)*int64(RecordSize)
}

func writeNewHeader(file *os.File) error {
    header := make([]byte, HeaderSize)
    copy(header[0:8], []byte("MINIDB01"))
    binary.LittleEndian.PutUint32(header[8:12], 1)

    _, err := file.WriteAt(header, 0)
    return err
}

func validateHeader(file *os.File, size int64) error {
    if size < int64(HeaderSize) {
        return fmt.Errorf("database file is too small to contain a valid header")
    }

    header := make([]byte, HeaderSize)
    if _, err := file.ReadAt(header, 0); err != nil {
        return err
    }

    if string(header[0:8]) != "MINIDB01" {
        return fmt.Errorf("not a MiniDB file: bad magic bytes")
    }

    version := binary.LittleEndian.Uint32(header[8:12])
    if version != 1 {
        return fmt.Errorf("unsupported database version %d", version)
    }

    dataBytes := size - int64(HeaderSize)
    if dataBytes%int64(RecordSize) != 0 {
        return fmt.Errorf("database file has a partial/corrupt record region")
    }

    return nil
}

func Open(path string) (*Store, error) {
    file, err := os.OpenFile(path, os.O_RDWR|os.O_CREATE, 0644)
    if err != nil {
        return nil, err
    }

    info, err := file.Stat()
    if err != nil {
        file.Close()
        return nil, err
    }

    if info.Size() == 0 {
        if err := writeNewHeader(file); err != nil {
            file.Close()
            return nil, err
        }
    } else {
        if err := validateHeader(file, info.Size()); err != nil {
            file.Close()
            return nil, err
        }
    }

    return &Store{file: file}, nil
}

func (s *Store) Close() error {
    return s.file.Close()
}

func encodeUser(u User) ([]byte, error) {
    if len([]byte(u.Name)) > MaxNameLen {
        return nil, fmt.Errorf("name is longer than %d bytes", MaxNameLen)
    }
    if len([]byte(u.Email)) > MaxEmailLen {
        return nil, fmt.Errorf("email is longer than %d bytes", MaxEmailLen)
    }

    record := make([]byte, RecordSize)

    binary.LittleEndian.PutUint64(record[0:8], uint64(u.ID))
    if u.Deleted {
        record[8] = 1
    }
    copy(record[9:41], []byte(u.Name))
    copy(record[41:105], []byte(u.Email))
    binary.LittleEndian.PutUint32(record[105:109], uint32(u.Age))

    return record, nil
}

func decodeUser(record []byte) (User, error) {
    if len(record) != RecordSize {
        return User{}, fmt.Errorf("expected %d bytes, got %d", RecordSize, len(record))
    }

    return User{
        ID:      int64(binary.LittleEndian.Uint64(record[0:8])),
        Deleted: record[8] == 1,
        Name:    strings.TrimRight(string(record[9:41]), "\x00"),
        Email:   strings.TrimRight(string(record[41:105]), "\x00"),
        Age:     int32(binary.LittleEndian.Uint32(record[105:109])),
    }, nil
}

func (s *Store) nextID() (int64, error) {
    info, err := s.file.Stat()
    if err != nil {
        return 0, err
    }

    count := (info.Size() - int64(HeaderSize)) / int64(RecordSize)
    return count + 1, nil
}

func (s *Store) Insert(name, email string, age int32) (int64, error) {
    id, err := s.nextID()
    if err != nil {
        return 0, err
    }

    record, err := encodeUser(User{
        ID:    id,
        Name:  name,
        Email: email,
        Age:   age,
    })
    if err != nil {
        return 0, err
    }

    if _, err := s.file.WriteAt(record, recordOffset(id)); err != nil {
        return 0, err
    }

    return id, nil
}

func (s *Store) Get(id int64) (User, error) {
    if id < 1 {
        return User{}, ErrNotFound
    }

    record := make([]byte, RecordSize)
    if _, err := s.file.ReadAt(record, recordOffset(id)); err != nil {
        if errors.Is(err, io.EOF) {
            return User{}, ErrNotFound
        }
        return User{}, err
    }

    u, err := decodeUser(record)
    if err != nil {
        return User{}, err
    }

    if u.Deleted {
        return User{}, ErrDeleted
    }

    // A zero ID in an allocated-looking slot is not expected in this format.
    if u.ID != id {
        return User{}, fmt.Errorf("record %d is corrupt: stored id is %d", id, u.ID)
    }

    return u, nil
}

func (s *Store) Scan() ([]User, error) {
    info, err := s.file.Stat()
    if err != nil {
        return nil, err
    }

    count := (info.Size() - int64(HeaderSize)) / int64(RecordSize)
    users := make([]User, 0, count)

    for id := int64(1); id <= count; id++ {
        u, err := s.Get(id)
        if errors.Is(err, ErrDeleted) {
            continue
        }
        if err != nil {
            return nil, err
        }
        users = append(users, u)
    }

    return users, nil
}

func (s *Store) Delete(id int64) error {
    if _, err := s.Get(id); err != nil {
        return err
    }

    _, err := s.file.WriteAt([]byte{1}, recordOffset(id)+8)
    return err
}

func printUser(u User) {
    fmt.Printf("id=%d name=%s email=%s age=%d\n", u.ID, u.Name, u.Email, u.Age)
}

func main() {
    if len(os.Args) != 2 {
        fmt.Println("usage: minidb <database-file>")
        os.Exit(1)
    }

    store, err := Open(os.Args[1])
    if err != nil {
        fmt.Println("open error:", err)
        os.Exit(1)
    }
    defer store.Close()

    scanner := bufio.NewScanner(os.Stdin)

    for {
        fmt.Print("minidb> ")
        if !scanner.Scan() {
            fmt.Println()
            break
        }

        parts := strings.Fields(scanner.Text())
        if len(parts) == 0 {
            continue
        }

        switch strings.ToUpper(parts[0]) {
        case "INSERT":
            if len(parts) != 4 {
                fmt.Println("usage: INSERT <name> <email> <age>")
                continue
            }

            age64, err := strconv.ParseInt(parts[3], 10, 32)
            if err != nil {
                fmt.Println("age must be a 32-bit integer")
                continue
            }

            id, err := store.Insert(parts[1], parts[2], int32(age64))
            if err != nil {
                fmt.Println("insert error:", err)
                continue
            }
            fmt.Printf("inserted id=%d\n", id)

        case "GET":
            if len(parts) != 2 {
                fmt.Println("usage: GET <id>")
                continue
            }

            id, err := strconv.ParseInt(parts[1], 10, 64)
            if err != nil {
                fmt.Println("id must be an integer")
                continue
            }

            u, err := store.Get(id)
            if err != nil {
                fmt.Println("get error:", err)
                continue
            }
            printUser(u)

        case "SCAN":
            if len(parts) != 1 {
                fmt.Println("usage: SCAN")
                continue
            }

            users, err := store.Scan()
            if err != nil {
                fmt.Println("scan error:", err)
                continue
            }
            for _, u := range users {
                printUser(u)
            }

        case "DELETE":
            if len(parts) != 2 {
                fmt.Println("usage: DELETE <id>")
                continue
            }

            id, err := strconv.ParseInt(parts[1], 10, 64)
            if err != nil {
                fmt.Println("id must be an integer")
                continue
            }

            if err := store.Delete(id); err != nil {
                fmt.Println("delete error:", err)
                continue
            }
            fmt.Printf("record %d deleted\n", id)

        case "EXIT", "QUIT":
            return

        case "HELP":
            fmt.Println("INSERT <name> <email> <age>")
            fmt.Println("GET <id>")
            fmt.Println("SCAN")
            fmt.Println("DELETE <id>")
            fmt.Println("EXIT")

        default:
            fmt.Println("unknown command; try HELP")
        }
    }

    if err := scanner.Err(); err != nil {
        fmt.Println("input error:", err)
    }
}

18. What you should understand before Part 2

Do not measure success by whether the program compiles. Measure it by whether you can explain the path of one value.

For example: Alice's age starts as an int32 in memory. encodeUser converts it into four little-endian bytes and places them at positions 105–108 inside a 256-byte record. If Alice has ID 1, that record begins at file offset 128, so her age lives at file offsets 233–236. A later process opens the same file, reads 256 bytes starting at 128, takes bytes 105–108 from that record buffer, decodes them as little-endian, and reconstructs the int32.

If you can tell that story for the ID, tombstone, name, email, and age—and if you understand why GET can jump directly while SCAN must visit every record—then Part 1 has done its job.

The path forwardPart 2 should not begin with “databases use pages.” It should begin with the pains we now possess: too many tiny direct file operations, no cache policy, wasted fixed-size fields, and no structure for managing variable-size records. Pages will become a solution to problems you already recognize.
